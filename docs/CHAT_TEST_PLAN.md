# 미검증 채팅·외부 연동 테스트 계획

## 1. 목적과 범위

현재 남아 있는 실제 웹·안드로이드 통신, PostgreSQL 연동, SMS 발송을 검증한다.
이 문서는 앞으로 수행할 계획이며 실행 결과나 실행 허가를 의미하지 않는다.

- 이미 통과한 채팅 회귀 테스트와 H2 기동 테스트는 이번 실행 목록에서 제외한다.
- 코드와 관련 환경이 그대로라면 기존 자동 테스트를 반복하지 않는다.
- 검증 중 코드를 수정하면 변경에 관련된 회귀 테스트를 실행한다.
- 테스트용 PostgreSQL과 운영 DB의 결과는 구분한다.
- 운영 DB 작업과 실제 SMS 발송은 허용된 대상·범위에서만 진행한다.
- 환경이 없는 항목은 미검증으로 남기고 독립적으로 가능한 항목을 진행한다.

## 2. 실행 준비

1. 코드 버전과 미커밋 변경 여부를 기록한다.
2. 서버 주소, 활성 프로필, DB·Redis 대상, ddl-auto를 확인한다.
3. 로컬 또는 테스트 환경임을 확인한 후 백엔드를 실행한다.
4. 테스트 계정을 준비한다: A는 게시글 작성자, B는 문의자, C는 비참여자이다.
5. A의 게시글 P와 B가 P에 문의하여 생성한 채팅방 R을 준비한다.
6. 각 계정의 액세스 토큰과 테스트 데이터 ID를 확보한다.

토큰, 비밀번호, 개인키, 전체 전화번호는 문서와 로그에 노출하지 않는다.
기본 웹 페이지는 /test.html이며 A와 B의 별도 탭을 사용한다.
비정상 경로·본문 검증에는 STOMP 요청을 직접 구성할 수 있는 클라이언트를 사용한다.

### 통신 정보

- 연결: /ws/chat
- STOMP CONNECT 헤더: Authorization: Bearer <accessToken>
- SEND: /app/chat/message
- SUBSCRIBE: /topic/chat/{roomId}
- 전송 본문: {"roomId": 1, "content": "실행별로 구분 가능한 메시지"}
- REST 요청에도 해당 사용자의 Bearer 액세스 토큰을 전달한다.
- 본문의 roomId는 준비한 R의 실제 ID로 교체한다.

## 3. 웹 클라이언트 종단간 검증

### WEB-01: 연결 및 양방향 송수신

1. A와 B가 자신의 토큰으로 CONNECT하고 동일한 R을 구독한다.
2. B가 고유한 내용의 메시지를 보내고 A와 B에서 수신을 확인한다.
3. A도 다른 메시지를 보내고 양쪽 수신을 확인한다.
4. 연결을 끊었다 다시 연결하고 구독한 뒤 송수신을 확인한다.

기대 결과: 정상 연결 및 양방향 수신. 단일 구독 기준 각 메시지가 한 번씩 수신된다.
현재 서버는 발신자에게도 메시지를 전달한다. CONNECT 성공만으로 구독 성공을 판정하지 않는다.

### WEB-02: 저장·목록·상대방 표시

1. 전송 후 GET /api/chatrooms/{R}/messages?offset=0&limit=10을 호출한다.
2. A와 B가 각각 GET /api/chatrooms 및 GET /api/chatrooms/{R}을 호출한다.
3. 응답을 전송한 내용과 비교한다.

기대 결과:

- 메시지 내용, 실제 발신자 ID, 메시지 ID, 생성 시각이 조회된다.
- 양쪽 목록에 R이 나타나고 조회자 기준 상대방 닉네임이 표시된다.
- 마지막 메시지와 시각이 갱신된다.

### WEB-03: 숨김·숨김 해제·방 재사용

1. B가 PATCH /api/chatrooms/{R}/hide를 호출하고 양쪽 목록을 조회한다.
2. A가 R에 새 메시지를 보내고 B의 목록을 다시 조회한다.
3. B가 다시 숨긴 후 POST /api/chatrooms에 {"postId": P의 실제 ID}를 보내 재문의한다.

기대 결과:

- 숨긴 직후 B의 목록에서만 R이 사라진다.
- A의 새 메시지 이후 B의 목록에 R이 다시 나타난다.
- 재문의 시 동일한 R이 반환되고 신규 방이 생성되지 않으며 숨김이 해제된다.

### WEB-04: 실제 STOMP 인증·권한 차단

각 시도를 별도로 실행한다. 오류로 연결이 종료되면 새 연결을 사용한다.

| 시도 | 기대 결과 |
|---|---|
| 토큰 없이 CONNECT | 인증 거절 |
| 만료된 액세스 토큰 또는 refresh token으로 새 CONNECT | 인증 거절 |
| C가 R 구독 후 A 또는 B가 메시지 전송 | C는 받지 못하고 정상 참여자는 수신 |
| C가 R로 메시지 전송 | 저장·전달되지 않음 |
| B가 본문의 senderUserId를 A의 ID로 지정 | 실제 발신자는 B로 저장·전달 |
| /topic/chat/{R}로 직접 SEND | 저장·전달되지 않음 |
| /topic/chat/* 구독 | 구독 거절 |

이 항목은 기존 단위 테스트 재실행이 아니라 실제 연결에서 인증·인터셉터·서비스가 함께 동작하는지 확인하는 검증이다.
거절 여부는 오류 표시, 정상 참여자의 수신, REST 조회 또는 DB 저장 여부를 함께 확인한다.
미수신 판정을 위한 관찰 시간을 실행 전에 정하고 결과에 기록한다.
연결 이후 토큰 만료에 따른 자동 종료는 이 계획의 범위가 아니다.

### WEB-05: 차단 관계

1. 현재 사용자 API에서 경로와 본문을 확인한 후 A가 B를 차단한다.
2. A와 B가 각각 상대방에게 고유한 메시지를 전송한다.
3. 수신 내역과 저장 결과를 확인한다.

기대 결과: 양쪽 메시지가 저장·전달되지 않는다.
후속 테스트에 필요하면 이번에 설정한 테스트 차단 관계를 해제한다.

## 4. 안드로이드 앱 검증

### APP-01: 실제 앱 송수신

1. 테스트 앱 또는 기기를 준비하고 기기에서 접근 가능한 서버 주소를 설정한다.
2. 앱에서 A 또는 B로 로그인하고 R에 진입한다.
3. 상대 계정의 웹 또는 다른 앱과 양방향으로 메시지를 주고받는다.
4. 화면 내용과 REST 조회 결과를 비교한다.

기대 결과: 인증된 연결, 정상 송수신, 실제 발신자 표시 및 저장. 발신 메시지가 화면에 중복 표시되지 않는다.
기기의 localhost를 개발 PC 주소로 사용하지 않는다.

### APP-02: 재진입·네트워크 재연결

1. 방을 나갔다가 다시 진입해 메시지를 보낸다.
2. 네트워크를 끊었다 복구한 뒤 재연결과 구독 복구 여부를 확인한다.
3. 메시지를 다시 보내 수신 횟수를 확인한다.

기대 결과: 복구 후 송수신이 가능하며 중복 구독·중복 표시가 없다.
앱이나 기기가 없으면 웹 결과와 구분하여 미검증으로 기록한다.

## 5. 테스트용 PostgreSQL 검증

### DB-01: 실제 DB 저장과 데이터 유지

1. 테스트용 PostgreSQL 연결과 DB를 초기화하지 않는 재시작 설정을 확인한다.
2. WEB-01~03을 수행하면서 chat_rooms, chat_room_members, messages를 확인한다.
3. 최종 메시지와 숨김 상태를 기록한다.
4. 백엔드만 재시작한 후 REST 조회와 DB 확인을 수행한다.

기대 결과: 방, 두 참여자, 메시지, 마지막 메시지 및 숨김 상태가 올바르게 저장되고 재시작 후에도 유지된다.
웹 검증을 처음부터 같은 PostgreSQL에서 수행했다면 동일한 생성·송수신을 반복하지 않고 해당 증거를 사용한다.
H2 성공이나 테스트용 PostgreSQL 성공을 운영 DB 성공으로 기록하지 않는다.

## 6. 실제 SMS 검증

### SMS-01: 발송·수신·인증

1. 실제 발송이 허용된 테스트 번호와 최대 발송 횟수를 확인한다.
2. 현재 AuthController에서 발송·검증 API와 인증번호 유효시간을 확인한다.
3. 테스트용 설정의 SMS 키와 등록 발신번호를 사용해 인증번호를 발송한다.
4. API 응답, 발송 서비스 내역, 실제 휴대폰 수신을 각각 확인한다.
5. 받은 코드로 인증을 요청한다.
6. 허용된 발송 횟수 안에서 별도 인증 흐름으로 잘못된 코드와 만료된 코드를 확인한다.

기대 결과: 실제 문자 수신과 유효 코드 인증 성공. 잘못된 코드와 만료된 코드는 거절된다.
성공 응답만으로 실제 수신 성공을 판정하지 않는다.
휴대폰 수신을 직접 확인할 수 없으면 사용자 확인이 필요하다고 기록한다.
실패 또는 응답 지연 시 확인 없이 반복 발송하지 않는다.

## 7. 운영 DB 검증 — 필요한 경우 별도 수행

### PROD-01: 연결·읽기

1. 허용된 대상 서버·DB와 읽기 범위를 확인한다.
2. 활성 프로필과 ddl-auto를 확인한다. create/create-drop을 적용하지 않는다.
3. 기존 운영 애플리케이션의 연결 상태와 허용된 API 또는 최소 조회를 확인한다.

기대 결과: 지정한 운영 DB에 연결되고 필요한 조회가 정상 동작한다.
이 검증을 위해 운영 서버를 임의로 재시작하거나 스키마를 변경하지 않는다.
불필요한 개인정보와 대량 데이터를 조회하지 않는다.

### PROD-02: 쓰기 — 명시적으로 허용된 경우만

1. 지정된 테스트 계정, 생성 데이터, 정리 범위를 확인한다.
2. 최소한의 채팅방 생성·메시지 저장·조회를 확인한다.
3. 생성 ID를 기록하고 허용된 방법으로 이번 생성 데이터만 정리한다.

기대 결과: 지정 범위의 저장·조회가 정상 동작하고 데이터 정리 결과가 기록된다.
읽기만 확인했다면 쓰기까지 검증했다고 보고하지 않는다.
운영 확인이 요청되지 않았거나 허용되지 않았다면 미검증 사유를 기록한다.

## 8. 결과 기록과 완료 판단

- 첫 실행 시 저장소 루트의 TEST_RESULTS.md를 생성하고 테스트 ID별로 기록한다.
- Gradle이 만드는 파일이 아니라 테스트 수행자가 작성하는 결과 문서이다.
- 실행 일시, 코드 버전, 환경, 클라이언트, 절차, 기대·실제 결과, 근거를 기록한다.
- 상태는 통과 / 실패 / 미검증으로 구분한다. 실행하지 않은 항목을 통과로 표시하지 않는다.
- 웹·안드로이드, 테스트 DB·운영 DB, SMS 응답·실제 수신 결과를 각각 구분한다.
- 실패 수정 후에는 실패 시나리오와 변경에 필요한 회귀 테스트만 우선 재검증한다.
- 이번 실행에서 만든 테스트 데이터와 실행한 프로세스만 정리한다.
- 요청 범위의 항목이 실패하거나 미검증이면 전체 검증 완료라고 보고하지 않는다.
