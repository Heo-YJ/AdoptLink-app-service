# AdoptLink 웹 화면과 사용자 흐름 초안

작성일: 2026-09-25

이 문서는 웹 전환을 위한 기획 초안이다. 사용자 확정 사항과 제안을 구분한다.
아래 웹 경로는 화면 설계를 위한 제안이며 현재 구현된 프론트 라우트가 아니다.
백엔드 API, 인증 정책, 안드로이드 프로젝트는 이 문서 작성으로 변경하지 않는다.

## 1. 확정 사항

- 비로그인 방문자도 분양 게시글 목록과 상세를 볼 수 있다.
- 게시글 작성과 채팅 이용에는 로그인이 필요하다. 개인 스크랩도 로그인 후 제공한다.
- 보호소 관리자는 별도 회원가입 유형이 아니다.
- 일반 회원이 보호소 관리자 신청을 하고 운영 관리자가 승인하면 기존 계정의 역할이 USER에서 SHELTER_ADMIN으로 바뀐다.
- 신청 접수만으로 역할이 바뀌지 않는다. 심사 대기·반려 상태에서는 일반 회원 역할을 유지한다.
- 운영 관리자(ADMIN)와 보호소 관리자(SHELTER_ADMIN)는 다른 역할이다.
- 일반 회원이 본인 보호소 정보·증빙을 함께 제출한다. 운영자가 승인하면 보호소가 공개되고 신청자에게 보호소 관리자 역할을 부여한다. 이후 소속 유기동물을 등록·관리한다.
- 사용자는 사이트 안에서 보호소 정보를 확인할 수 있다. 추후 지도에서 보호소를 선택하면 같은 보호소 상세 화면으로 연결한다.
- 첫 단계는 일반 사용자용 웹이다. 운영 관리자 화면은 다음 단계로 미룬다.
- 안드로이드 프로젝트는 메인·서브 컬러 참고용으로 사용한다. 화면 배치를 그대로 옮기는 요구는 없다.

## 3. 메뉴와 화면 목록 — 제안

PC와 휴대폰에서 사용할 수 있는 반응형 웹을 기본안으로 한다.
첫 화면은 게시글 탐색에 집중하고 별도의 홍보용 랜딩 화면은 우선 두지 않는다.

- 공통 메뉴: 동물 찾기, 공지사항.
- 비로그인 우측 메뉴: 로그인, 회원가입. 글쓰기 버튼은 로그인 안내로 연결.
- 로그인 우측 메뉴: 글쓰기, 채팅, 마이페이지. 스크랩은 마이페이지에서 접근.
- 보호소 관리자 신청과 상태 확인은 마이페이지 안에 배치. 승인 후에는 내 보호소 관리로 연결.
- 운영 관리자 메뉴는 일반 회원 메뉴와 분리하며 다음 단계에 제작.

동물 정보는 현재 코드의 종류, 품종, 성별, 나이, 중성화 여부를 기준으로 한다.
지도 화면은 후속 단계로 확정했다. 첫 단계에는 보호소 상세와 동물 정보 구조를 정리하고, 지도는 같은 상세 화면을 재사용한다.
지역 검색·고급 필터의 세부 범위는 아직 정하지 않았다.

## 4. 주요 사용자 흐름

### 4.1 탐색에서 채팅 문의까지

1. 방문자가 목록에서 게시글 상세로 이동한다.
2. 비로그인 상태에서 채팅 버튼을 누르면 로그인 필요 이유를 안내하고 로그인 화면으로 이동한다.
3. 로그인 후 원래 게시글과 문의 흐름으로 돌아간다. 회원가입을 거쳐도 돌아갈 게시글을 유지한다.
4. 서버에서 기존 방 또는 새 방을 확인해 채팅방으로 이동한다.
5. 사용자가 내용을 입력하고 전송한다. 로그인 완료만으로 메시지를 자동 전송하지 않는다.
6. 이미 문의한 게시글이라면 기존 대화를 이어간다.

본인 게시글에서는 채팅 문의 대신 수정·분양 상태 변경 등 작성자 행동을 표시한다.
비참여자의 채팅방 직접 접근은 차단한다.

### 4.2 게시글 작성과 분양 완료

1. 글쓰기를 선택한다. 비로그인이라면 로그인 후 작성 화면으로 돌아간다.
2. 사진, 제목, 본문, 동물 정보를 입력하고 등록한다.
3. 등록 성공 시 해당 게시글 상세로 이동한다.
4. 작성자는 문의 채팅을 확인하고, 분양이 끝나면 완료로 변경한다.
5. 삭제는 확인 절차를 거쳐 처리하고 목록으로 이동한다.

완료 게시글의 신규 문의 허용 여부와 수정 가능한 동물 정보 범위는 상세 화면 설계 때 확정한다.
현재 코드의 상태 값은 AVAILABLE, COMPLETED 두 가지이며 예약 상태는 추가하지 않는다.

### 4.3 일반 회원에서 보호소 관리자로

일반 회원(USER) → 마이페이지 → 보호소 정보·증빙 제출 → 운영자 승인 → 보호소 공개 및 관리자 역할 부여 → 소속 동물 등록.

- 승인: 보호소가 공개되고 기존 계정이 SHELTER_ADMIN으로 전환되며 승인 상태를 표시한다.
- 반려: USER를 유지하며 반려 사유를 표시한다.
- 대기 중: 보호소는 공개하지 않으며 일반 회원의 기존 기능을 계속 사용할 수 있다.
- 승인 시 회원 데이터와 기존 게시글·채팅은 같은 계정에 유지한다.
- 승인된 권한이 웹 화면과 인증 상태에도 반영되도록 한다. 구체적인 인증 갱신 방식은 구현 단계에서 정한다.

신규 보호소 등록과 관리자 승인을 연결하는 순서는 확정했다. 반려 후 재신청 정책은 상세 설계에서 정한다.
기존 보호소 선택만으로는 신규 보호소 운영자의 신청을 처리할 수 없으므로 신규 보호소 정보·증빙을 함께 제출하는 화면이 필요하다.
제출한 증빙은 심사용으로 취급하며 방문자가 보는 보호소 상세에는 표시하지 않는다.

### 4.4 보호소와 소속 동물 관리

1. 승인된 보호소 관리자는 마이페이지에서 본인 보호소 관리로 이동한다.
2. 신청 시 제출해 승인된 보호소 소개·사진·주소·공개 연락처 등을 확인하거나 수정한다. 구체적인 필수 항목과 수정 후 재심사 범위는 폼 설계 시 정한다.
3. 해당 보호소에 속한 유기동물의 사진·동물 정보·분양 상태를 등록한다.
4. 방문자는 보호소 상세에서 보호소 정보와 소속 동물 목록을 확인한다.
5. 방문자가 동물을 선택하면 상세 정보를 보고 로그인 후 채팅으로 문의한다.
6. 지도 기능을 추가하면 지도에서 보호소 선택 → 기존 보호소 상세로 연결한다.

일반 회원은 본인의 일반 분양 게시글을 작성하고, 보호소 관리자는 소속 보호소와 연결된 동물 정보를 관리한다.
관리자 역할만으로 다른 보호소의 정보·동물을 수정할 수 없도록 소속 권한을 구분한다.
동물 정보와 기존 분양 게시글을 하나로 연결하는 안을 우선 제안한다. 별도 동물 프로필과 게시글을 나눌지는 상세 설계에서 정한다.
지도 도입 전에는 동물 상세의 보호소명에서 보호소 상세로 이동하는 경로를 제안한다.

### 4.5 채팅 재진입과 연결 복구

- PC는 채팅 목록과 대화를 나란히, 휴대폰은 목록과 대화를 별도 화면으로 보여주는 안을 제안한다.
- 방 진입 시 저장된 메시지를 불러오고 실시간 메시지를 이어서 받는다.
- 연결 중·연결 끊김·재연결 실패를 사용자가 구분할 수 있게 표시한다.
- 숨김은 요청한 사용자의 목록에만 적용하고 상대방의 새 메시지에 따라 복구한다.
- 연결 복구 시 중복 구독과 중복 표시를 방지한다.
- 현재 미구현인 읽지 않은 메시지 수·읽음 표시는 실제 구현 전까지 정확한 값처럼 표시하지 않는다.

## 5. 공통 화면 상태와 백엔드 연동 과제

각 화면에는 로딩, 결과 없음, 입력 오류, 요청 실패, 재시도 상태를 설계한다.
삭제된 게시글, 권한 없는 채팅방, 만료된 로그인에는 이유와 돌아갈 경로를 제공한다.
채팅 전송 실패 시 입력한 내용을 유지하고 실패 여부를 보여준다.

| 항목 | 현재 확인한 코드와의 차이 또는 필요한 작업 |
|---|---|
| 비로그인 게시글 탐색 | 현재 일반 API는 인증을 요구한다. 목록·상세 GET만 공개하고 작성·수정·삭제 등은 인증·소유권 검사를 유지해야 한다. |
| 로그인 복귀 | 로그인 전 목적 화면을 보존하고 내부 경로로만 복귀하도록 구현해야 한다. |
| 작성자 정보 공개 | 게시글 공개와 함께 제공할 작성자 정보 범위를 정하고 전화번호·로그인 ID 등 계정 정보는 공개 응답에 넣지 않는다. |
| 보호소 정보·소속 동물 | 보호소 등록·수정·공개 상세와 동물-보호소 연결, 소속 관리자 권한 검사가 필요하다. 현재 일반 게시글 기능만으로 완료된 기능이라고 보지 않는다. |
| 이미지 선택 | 현재는 이미지 URL 저장 기능이다. 실제 업로드와 실패 처리는 별도 연동 작업이다. |
| 신규 보호소 신청 | 현재 신청은 facilityId를 요구한다. 보호소 정보·증빙 동시 제출 → 승인 시 공개·역할 부여 계약으로 보완해야 한다. 기존 보호소 선택 경로와의 관계도 정한다. |
| 운영 관리자 화면 연기 | 심사 화면을 미뤄도 승인 절차 자체는 필요하다. 첫 연동 검증은 기존 관리자 API 또는 승인된 테스트 계정으로 수행할 수 있도록 준비한다. 일반 회원에게 관리자 권한을 주거나 자동 승인하는 방식으로 대체하지 않는다. |
| 지도 연결 | 후속 지도에서 기존 보호소 상세로 연결한다. 주소·좌표·공개 범위는 지도 구현 전 구체화한다. |
| 완료 게시글 | 현재 검색은 AVAILABLE 중심이다. 완료 글 노출·신규 문의 정책에 따라 조회 조건을 조정해야 한다. |
| 권한 전환 | 승인 후 기존 로그인 상태에 새 역할을 반영하는 처리가 필요하다. |
| 기존 오류 | REST 토큰 종류 구분, 게시글 수정 인자 순서, 탈퇴·삭제 상태 처리는 연동 전 보완 대상이다. |

위 항목은 구현 완료 목록이 아니다. 이번 작업에서는 API·인증 계약을 변경하지 않는다.

## 6. 결정 대기 사항

이번 대화에서 추가 확정한 사항:

- 보호소 관리자의 보호소 등록과 소속 유기동물 정보 관리.
- 사이트 내 보호소 상세, 추후 지도에서 해당 상세로 이동.
- 일반 사용자 화면 우선, 운영 관리자 화면은 다음 단계.

- 신규 보호소 정보·증빙을 신청 시 함께 제출하고 운영자 승인 시 보호소 공개와 관리자 역할 부여를 수행한다. 소속 동물 등록은 승인 이후다.

이후 해당 화면을 구체화할 때 정할 사항:

- 분양 완료 게시글의 신규 문의 허용 여부.
- 보호소 신청 반려 후 수정·재신청 허용 여부.
- 게시글 작성 후 동물 정보 수정 허용 범위.
- 보호소 동물 정보와 분양 게시글을 하나로 연결할지, 별도 프로필로 관리할지.

## 7. 다음 작업 제안

메인 목록, 게시글 상세, 보호소 상세 세 화면의 와이어프레임부터 작성한다.
와이어프레임은 실제 서비스 구현에 앞서 정보·버튼 위치와 화면 이동을 확인하는 화면 초안이다.

1. 메인 목록: 탐색 메뉴, 검색·정렬, 게시글 카드, 로그인·글쓰기 진입을 배치한다.
2. 게시글 상세: 사진, 동물 정보, 작성자 또는 소속 보호소, 분양 상태, 스크랩·채팅 문의를 배치한다.
3. 보호소 상세: 보호소 소개, 위치·공개 연락처, 소속 동물 목록과 동물 상세 진입을 배치한다.
4. 비로그인 방문자의 열람 → 로그인 요청 → 원래 게시글 복귀 동선을 연결한다.
5. 같은 정보를 PC와 휴대폰에서 어떻게 배치할지 비교한다.

이 세 화면의 구조를 정한 뒤 로그인·회원가입, 게시글 작성, 보호소 신청, 채팅 화면을 구체화한다.

답변 전에는 위 항목을 확정된 요구사항으로 취급하지 않는다.
현재 산출물은 화면·흐름 초안이며 프론트 구현, 서버 실행, 통합 테스트, 배포는 수행하지 않는다.
